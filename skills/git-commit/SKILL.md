# Git Commit

## 工作流程

1. **先执行 `git status`**，了解当前分支、暂存区、未暂存修改和未跟踪文件的全貌。没有可提交改动时直接说明，不创建空提交。
2. 阅读 `git diff`、`git diff --cached`，并检查与提交范围有关的未跟踪文件内容。不能仅凭文件名或统计信息编写提交说明。
3. 根据改动目的决定提交数量：同一功能及其必要的测试、文档放在一起；独立的功能、修复或清理拆成多个 commit。不要因为文件多就机械拆分，也不要把无关改动塞进一个 commit。用户指定了提交范围时，以该范围为准。
4. 简要说明分组，随后执行已获用户授权的提交，不重复请求确认。若用户只要求生成提交信息，则只输出信息，不执行暂存或提交。
5. 每次只暂存当前分组的文件或代码块，检查 `git diff --cached`，确保实际暂存内容与本次提交说明一致。特别注意原先已暂存的内容，不要顺带提交范围外的改动；调整分组时保留工作区内容，不丢弃用户修改。
6. 完成各次提交后，再执行 `git status`，报告每个 commit 的短哈希、标题，以及剩余未提交的改动。提交失败时说明原因，不把失败报告为成功，也不擅自绕过提交钩子。

## 提交信息

- 使用英文 key（类型）和中文内容：`<type>: <中文摘要>`；需要标明模块时可用 `<type>(<scope>): <中文摘要>`，scope 使用简短英文模块名。
- 常用类型：`feat` 新功能、`fix` 修复、`refactor` 重构、`docs` 文档、`test` 测试、`style` 格式、`perf` 性能、`build` 构建、`ci` 持续集成、`chore` 杂项维护。按实际改动选择类型。
- 摘要明确说明做了什么，避免“更新代码”等空泛表述。摘要和正文使用中文，代码标识符、技术名词可保留英文。
- 简单改动只写标题。单个 commit 内容较多、包含多个相关要点或需要解释原因时，使用标题、一个空行、中文正文。正文可以是段落或列表，说明关键改动及必要原因，不重复标题，不虚构测试结果。
- 多个 commit 分别编写信息；详细正文不能替代对独立改动的拆分。

简单提交：

```text
fix: 修复登录状态过期后无法跳转的问题
```

内容较多的提交：

```text
feat: 支持批量导出订单

新增按筛选条件导出订单的入口，复用现有订单查询逻辑。
对导出数量设置上限，并补充空结果和超限场景的测试。
```

使用真实换行写入提交信息，推荐通过 `git commit -F <消息文件>` 或分别传入标题和正文的 `-m` 参数，避免把字面量 `\n` 写入信息。

## 操作范围

默认只创建本地 commit。除非用户明确要求，不执行 push、amend 或其他历史重写操作。
